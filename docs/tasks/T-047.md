## T-047: Keyset pagination with declared fallback strategy

- **Status**: done
- **Size**: L
- **Implements**: D-010
- **Depends on**: T-009
- **Acceptance**: Structured browse paginates by keyset on the primary key or `_id` with the key appended as tiebreaker when sorting by another column, views, aggregations, and keyless relations fall back to LIMIT/OFFSET, and the driver declares which strategy it used.

- **Date done**: 2026-11-06

- **Notes**: Keyset on the primary key (read from `pg_index` in key order),
  appended as tiebreaker after the requested sort; the cursor predicate is an
  expanded OR-chain so mixed ASC/DESC sorts are correct. Falls back to
  LIMIT/OFFSET — declared with the reason in `ExecutionResult.page`
  (`PageInfo::Keyset{key,next_cursor}` / `Offset{reason,next_offset}`) — for
  views/matviews, keyless tables, and sorts on nullable columns (NULL ordering
  breaks keyset comparisons). A cursor that does not match the strategy or the
  key arity is refused. The browse stream's `Done` event carries the page too.
  Verified live: walking every page of a 1000-row table (page size 37, sort
  on a column with heavy ties, descending) returns each row exactly once in
  `ORDER BY grp DESC, id` order; the view walk by offset is exact too.
  **Not done:** a "Load more" control in the grid — the UI does not page yet.

  failed once under a fully parallel workspace run (timing-based 300ms wait);
  it passes alone.
