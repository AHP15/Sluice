## T-052: Decouple socket draining from webview consumption with a spill buffer

- **Status**: dropped
- **Size**: M
- **Implements**: D-010
- **Mitigates**: R-042
- **Depends on**: T-049
- **Acceptance**: The core drains each result at server speed into a memory-capped, disk-backed spill buffer in the cache dir and the credit protocol feeds the webview from that buffer, so a paused or hidden grid never halts a script between statements, with idle-transaction rollback and the statement timeout applying to batch execution.

- **Date dropped**: 2026-11-06
- **Notes**: Dropped as redundant. The coupling R-042 describes is not reachable in the shipped design: the credit protocol (T-049) gates only structured browse, a single autocommit SELECT. Raw scripts, pooled and pinned, never go through credit; T-050's `collect_budgeted` drains every result at server speed, skipping rows past the budget without decoding them, and returns the whole outcome sequence in one response, so no grid state can hold a script between statements. The statement timeout already bounds the whole batch (`execution::run` wraps both `run_script` and `run_in_editor`), pooled scripts cannot leave a transaction open past the call (a dirty lease is reset on release), and pinned explicit transactions have the editor's idle-rollback reaper. A spill buffer would have nothing to feed. The property is pinned by `a_script_drains_past_a_large_result_and_leaves_no_transaction_open` in crates/sluice-postgres/tests/budget_live.rs. Revisit if raw scripts ever start streaming to the webview through credit.
