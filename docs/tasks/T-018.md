- **Notes**: R-008's guard sits in the encoding path exactly as the risk demands, and
  further than expected: the ceiling is applied **in SQL**, via
  `CASE WHEN octet_length(...) > ceiling THEN NULL ELSE ... END` plus a
  companion length column, so an oversized value is never sent at all rather
  than sent and discarded. Verified live that a 2MB `text` and a 500KB `bytea`
  come back as `WireValue::Oversized` carrying the exact byte length, that a
  small value in the same column is unaffected, and that raising the ceiling
  inlines the 2MB value normally. `bytea` sizes report true stored bytes, not
  the inflated base64 length. The handle encodes relation + `ctid` + column;
  `ctid` is a physical pointer, so an UPDATE or `VACUUM FULL` invalidates it and
  the fetch reports "that row has changed" rather than silently returning a
  different row's data. Both actions exist: `fetch_value` loads one cell on
  demand, and `save_value_to_file` streams it in 1 MiB `substr` chunks straight
  to disk. TENSION RESOLVED, worth recording: saving server-side rather than via
  a webview download is deliberate — routing the bytes through the webview would
  put a 50MB blob back in the process D-007 is keeping small, and would need the
  `fs`/`dialog` plugins T-021 deliberately omits. The destination is derived in
  the core (downloads dir, sanitized name) rather than accepted from the webview,
  which would hand database content a write primitive.
