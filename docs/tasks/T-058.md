## T-058: Null-safe optimistic concurrency with declared column comparability

- **Status**: done
- **Size**: M
- **Implements**: D-027
- **Depends on**: T-056
- **Acceptance**: The concurrency predicate uses a null-safe comparison per engine rather than bare `=`, each column declares whether it is concurrency-comparable, non-comparable columns are excluded from the predicate with the UI stating the edit is protected by unique key only, and a conflict names which columns were unprotected.

- **Notes**: Postgres compares each written column against its value as read
  with `IS NOT DISTINCT FROM` (key columns keep `=`, since the gate guarantees
  they are NOT NULL). `ColumnDesc.concurrency_comparable` is declared per
  column from an allowlist in `encode::concurrency_comparable` (bool,
  integers, numeric, money, text types, uuid, date and time types, bytea).
  `json`, `xml`, floats and every unlisted type are false until T-060 probes
  the catalog. It defaults to false on the wire, so a guarantee is never
  assumed. Non-comparable or value-incomparable originals (oversized,
  structural) are left out and reported in `Affected.concurrency_omitted`. A
  zero-row update probes by key, so the conflict says "changed since it was
  read" or "not found" and names the unprotected columns. The grid footer
  names staged columns protected by unique key only before apply. Verified
  live: a NULL cell edits without a spurious conflict, a concurrent change is
  caught and rolled back, and a `json` edit goes through on the key with
  `doc` reported. SQL Server's INTERSECT form waits for that driver.
