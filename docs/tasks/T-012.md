## T-012: Transactional context on the execution result

- **Status**: done
- **Size**: M
- **Implements**: D-029
- **Mitigates**: R-041
- **Depends on**: T-010
- **Acceptance**: The execution result carries which transaction mode the batch ran under and, on failure, what was rolled back, and the editor summary distinguishes `statements 1-2 rolled back` from `statements 1-2 committed` rather than reporting bare per-statement success.

- **Notes**: `TxContext` carries the mode the batch actually ran under (`ImplicitSingle` /
  `ExplicitUser` / `AutocommitPerStatement`) and a disposition saying what
  survived, with `RolledBack` naming the undone ordinals. The R-041 test is the
  point: identical outcome sequences with different tx context must produce
  different summaries, and they do — `statement 3 failed; statements 1-2 rolled
  back` vs `... committed`. Verified live end to end: a three-statement batch
  failing on the third reports `RolledBack`, and the database is then checked to
  confirm the first two rows really are absent. The summary is computed in Rust
  and returned to the editor via `ScriptRun.summary` rather than re-derived in
  TypeScript, so there is one tested implementation. Two design notes: the
  failing statement's ordinal is recovered by intersecting the error's position
  hint with T-011's spans, so a mid-script failure is not blamed on statement 1;
  and because tokio-postgres discards partial results on a failed batch, the
  envelope reports one correctly-attributed error plus the rolled-back set
  rather than fabricating "successes" that were in fact undone — which is the
  more truthful reading of R-041 even though D-029's prose describes emitting
  the earlier successes.
