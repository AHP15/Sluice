## T-016: Lossless wire value encoding with per-column type descriptors

- **Status**: done
- **Size**: L
- **Implements**: D-006
- **Acceptance**: Each result set carries one type descriptor per column, large integers, arbitrary-precision decimals, temporals, binary, uuid, and exotic types cross as tagged strings while only booleans, small integers, and f64-native floats go raw, and cells distinguish present value, SQL NULL, and field-absent.

- **Notes**: The mechanism is the interesting part: rather than decoding Postgres' binary
  format per type, the browse compiler asks **the server** to render non-native
  columns by selecting them as `(col)::text` (and `encode(col,'base64')` for
  bytea). One choice delivers D-006, R-014 and R-008 at once. D-006's split is
  implemented literally — only `bool`, `int2`/`int4` and `float4`/`float8` go
  raw; `int8`, `numeric`, all temporals, `uuid`, binary and exotic types cross
  as tagged strings. Verified live against PostgreSQL 17: `int8` max
  (9223372036854775807) and `numeric(40,20)` round-trip digit-for-digit,
  `timestamptz` keeps sub-second precision and its offset, bytea arrives as
  base64 (a tagged string, not a JSON array of ints), and each column carries
  the engine's own type name. Contract changes this forced in sluice-core:
  `WireValue::Bytes` became a base64 `String` rather than `Vec<u8>`, since serde
  renders a byte vector as a JSON integer array — larger than base64 and
  contrary to T-016's "tagged string" requirement. Cell states: present value,
  SQL NULL and field-absent are three distinct variants (`Null` vs `Missing`),
  tested; Postgres never emits `Missing` because SQL has no absent columns, but
  the distinction is modelled for D-018's schemaless work.
