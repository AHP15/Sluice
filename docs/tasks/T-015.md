## T-015: Literal string matching and declared case-sensitivity for filters

- **Status**: done
- **Size**: M
- **Implements**: D-005
- **Mitigates**: R-009
- **Depends on**: T-013
- **Acceptance**: `contains`/`starts with`/`ends with` escape `%`, `_`, and the escape character in the bound value and emit an explicit `ESCAPE` clause, and case sensitivity is read from the server collation into the capability descriptor with an explicit per-operator case-insensitive toggle compiled per engine.

- **Date dropped**:
- **Notes**: Literal matching was already right (T-009): `%`, `_` and `\`
  escaped in the bound needle with an explicit `ESCAPE '\'`. Case handling
  was **not** what R-009's triaged guard asks for: `contains`/`starts_with`
  forced `ILIKE`, overriding the engine rather than reporting it. Now the
  default follows the engine — `LIKE` and plain `=` — and the descriptor says
  what that means: the database's default collation is read at connect
  (`datcollate`, and `collisdeterministic` of the default collation) into
  `Capabilities::string_collation`, and each string operator's
  `case_sensitive` is derived from determinism. The explicit toggle is
  `Predicate::case_insensitive` (serde-default, so existing payloads are
  unchanged), offered where `FilterOpDecl::case_insensitive_toggle` is set:
  `eq`/`ne`/`in` compile to `lower(col::text) … lower($n::text)`, the LIKE
  family to `ILIKE`, still literal. The toggle is refused, not ignored, on
  non-text columns and non-string operators. **Behaviour change:** a default
  `contains "a"` no longer matches `GAMMA` on Postgres; two tests that pinned
  the old `ILIKE` default were updated to set the toggle. Verified live against
  `en_US.utf8` (deterministic). Not done: per-column collations (a column with
  a nondeterministic ICU collation differs from the database default) — the
  descriptor reports the database default; and the filter-bar UI (T-014).
