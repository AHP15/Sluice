- **Notes**: Safety mode: a one-round-trip catalog probe at connect (standby; superuser; INSERT/UPDATE/DELETE/TRUNCATE on any table; CREATE in any schema or the database; CREATEROLE/CREATEDB) yields Capabilities.read_only = enforced{basis} | not_enforced{reasons} | unknown, and never fails a connect. default_transaction_read_only is reported but never counted as enforcement. Profiles carry `read_only = true` as intent; Guardrails.safety_mode pairs it with the probe (replacing SafetyMode::Unknown, per the T-027 note), and the UI is loud when it is requested but not enforced. No app-side write block: D-027 puts the guarantee in the database. Live test verified against the dev server (superuser not enforced, SELECT-only role enforced, an INSERT grant flips it). Production confirmation: sluice_core::dangerous_statements flags DDL, DO/CALL, and DELETE/UPDATE without WHERE at any depth (data-modifying CTEs, EXPLAIN ANALYZE), on code only (literals and comments stripped by the T-025 tokenizer), and is conservative on unparseable text. The core gates run_script and run_in_editor from the session's own Guardrails.production.armed; a refusal carries hints.confirmation {phrase = database name, statements}, and the exact phrase re-runs it.
