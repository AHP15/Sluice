- **Notes**: Every session — discovered, config-evaluated, command-line, or
  typed — is materialized core-side (`AppState.sessions`) with the same
  `Guardrails` field set: provenance, saved, production guard (armed + reasons),
  history, safety mode. Launched sessions default to history **off**, safety
  mode **unknown**, unsaved. The production guard arms for any host not
  provably loopback (a hostname cannot be classed private without resolving it,
  and guessing permissive is R-002's failure) and for `prod`/`production`/`prd`/
  `live` tokens in the host or database name — even on loopback, since an SSH
  tunnel to production is `localhost`. Typed connections run the same heuristic.
  The UI's guardrail bar always shows provenance, "not saved", history, safety
  mode, and why production confirmation is armed. "Save as profile" moves any
  inline password into the keychain inside the core (D-007; the response is
  checked for credential-shaped keys) and switches the session to normal
  profile handling (history on unless production), keeping the production flag.
  **Scope (same owner rule as T-026):** this task *arms* the guardrails; the
  enforcing features read them from the core when they land — typed
  confirmation is T-061's, history recording T-035's, and persisting a saved
  profile across restarts T-036's. Until then no session of any provenance is
  enforced, so discovered sessions are at parity rather than below it, which is
  R-002's actual failure. Each of those tasks carries a note.
