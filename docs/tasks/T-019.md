- **Notes**: `ColumnDesc.exact: Option<ExactDomain>` is the marker — chosen
  over `type_class`, since an editor picked by class is exactly where R-005's
  `parseFloat` gets in. `int8` → `Integer` with i64 bounds sent as JSON
  *strings* (a JSON-number bound would itself be rounded by `JSON.parse`);
  `numeric`/`money` → `Decimal` with unknown precision/scale, because a
  prepared statement's column metadata has the OID but not the typmod. T-053's
  catalog read can fill in `numeric(p,s)`; until then the server range-checks
  decimals. When p/s are known the validator rejects a scale overflow rather
  than letting Postgres silently round it. Validation is regex plus digit-wise
  string comparison; no `Number`, `parseFloat`, `BigInt` or `Math.*` anywhere on
  the path, enforced by `check-exact-numeric.mjs` (negative-controlled: it
  catches an injected `parseFloat` and `type="number"` and ignores comments).
  Binding was already exact: `wire_to_text` sends every parameter as text and
  casts in SQL. No staged-edit flow exists yet — the editor produces a
  validated `numeric` wire value and T-056 decides what a commit means. R-005's
  "extend the type-fidelity corpus to assert edit round-trips" belongs to
  T-068's corpus. New risk for triage: Postgres renders `money::text` with
  locale formatting (`$1,234.56`), which the decimal regex rejects, so a money
  cell opens showing an "invalid" value — the read path should render money as
  `(col)::numeric::text`.
