## T-021: TLS verification defaults and webview hardening

- **Status**: done
- **Size**: M
- **Implements**: D-007

- **Acceptance**: TLS certificate verification is on by default with an explicit per-profile opt-out that renders a visible warning, database values render as text nodes with no `innerHTML` path, and Tauri v2 capabilities are scoped to only what the app uses.

- **Notes**: Three clauses, three mechanisms. (1) TLS: `TlsMode::Verify` is the `Default`,
  built from the platform trust store with a webpki-roots fallback so a missing
  store fails closed rather than trusting nothing or everything; the opt-out is
  a named serializable mode, and the warning text is derived FROM the mode and
  travels to the UI with the session, so a connection cannot be in the unsafe
  state while the UI shows nothing. Tested that every non-Verify mode yields a
  warning. (2) No `innerHTML` path: every database value reaches the DOM through
  `{string}` in `ResultGrid`/`Navigator`, and `scripts/check-webview-safety.mjs`
  fails the build on `dangerouslySetInnerHTML`, `innerHTML`/`outerHTML`
  assignment, `insertAdjacentHTML`, `eval`, `new Function` and `document.write`
  — with a loud greppable opt-out marker so it stays a guard rather than an
  obstacle. Runs as part of `bun run build`; 11 files clean. (3) Capabilities
  scoped: `capabilities/default.json` grants only `core:app`, `core:event`,
  `core:window` and `core:webview` defaults. Deliberately absent are fs, shell,
  http, dialog, process, clipboard and updater — the webview renders hostile
  database content, so a capability it does not need is one an XSS cannot reach
  for. That omission is what forced T-018's save-to-file to be server-side, and
  the two tasks are consistent by design rather than by accident. Verified the
  app binary starts with this capability set and registers all nine commands
  without error; the rendered window was not visually inspected because macOS
  screen-recording permission is not granted to this terminal.
