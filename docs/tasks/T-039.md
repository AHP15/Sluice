- **Notes**: Before this, the pool used `RecyclingMethod::Fast` with no reset
  at all: a raw script's `SET`, open `BEGIN`, temp table or `PREPARE` leaked
  into whichever browse request drew that connection next. Every checkout now
  goes through `with_lease`, which runs the body on a `Lease` and releases it
  through the driver's declared `reset` on success, error and early return.
  `Native`: `ROLLBACK` then `DISCARD ALL` as **separate** statements (together
  in one simple query they would form an implicit transaction block, exactly
  where `DISCARD ALL` refuses to run), then the client statement cache is
  cleared. `ReopenOnly`: the connection is detached (`Object::take`) and closed;
  the pool opens a fresh one. `NotApplicable`: rollback only. A failed reset is
  treated as dirty and closed, and a lease dropped without release (panic,
  forgotten path) detaches rather than leaks. Counters (`pool_stats()`):
  releases, resets, reopens, clean returns. Capabilities report the driver's
  actual `reset`. Live tests run on a pool of **one**, so "the next request saw
  clean state" cannot just mean "got another connection": settings, open and
  aborted transactions, temp tables and prepared statements are all gone, the
  backend pid is unchanged under `Native` (a reset, not a reconnect) and
  changes under `ReopenOnly`. Mutation check: making release skip the reset
  fails 5 of the 6 tests. For now every lease is treated as dirty; T-040
  narrows that to what can actually mutate session state.
