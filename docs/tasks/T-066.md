- **Notes**: All three layers land: an `ErrorKind` enum matching D-017's list exactly (with
  `Unknown` first-class, and TLS folded into `ConnectionFailed` rather than
  adding a mapping obligation), optional `ErrorHints` for position/constraint/
  column/table/schema/retryable, and `EnginePayload` keeping SQLSTATE, severity
  and the engine's text verbatim. `Cancelled` is a distinct kind and
  `is_failure()` returns false for it. Partial failure is modelled per statement
  (`OutcomeBody::Error` inside the sequence) and per document (`DocumentError`
  on `Affected`) — the per-document half exists now because T-073 established
  Mongo's outcome sequence is permanently length 1, so without a channel inside
  one outcome Mongo would have nowhere to report bulk-write partials.
  FINDING, worth re-triage: **D-017's premise that Postgres reports a BYTE
  offset is wrong.** The protocol spec defines the `P` field as 1-based and
  measured in characters, and a live test against PostgreSQL 17 confirms it
  (`error_position_is_measured_in_characters_not_bytes`). A conversion is still
  required, just not the one named — the webview is JavaScript, where indices
  are UTF-16 code units, and a codepoint index diverges from a UTF-16 index on
  any astral character. `QueryPosition` therefore carries both units explicitly
  rather than an unlabelled integer. The guard's intent (never highlight the
  wrong character in non-ASCII text) is delivered; the decision's stated
  mechanism was inaccurate. LIMITATION: on the Postgres raw path
  tokio-postgres returns a single `Err` for a failed simple-query batch with no
  partial messages, so the successful statements' outcomes are genuinely
  unavailable — see T-012's note for how the envelope stays truthful anyway.
