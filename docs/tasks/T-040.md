## T-040: Reset only connections that were actually dirtied

- **Status**: done
- **Size**: M
- **Implements**: D-028
- **Mitigates**: R-036
- **Depends on**: T-039
- **Acceptance**: A connection is marked dirty only by raw passthrough, an explicit `SET`/`USE`, temp table DDL, or a prepared statement, structured browse traffic never dirties one, a clean connection is released without reopen, and reopen rate is instrumented.

- **Notes**: Leases start clean; only the raw passthrough path marks one
  dirty. On this driver that is the sole path that can carry `SET`, temp-table
  DDL, `PREPARE` or a dangling `BEGIN` — browse, navigator and value fetch are
  parameterized SELECTs, and tokio-postgres closes the named statements it
  prepares for them on drop, before release (asserted: zero rows in
  `pg_prepared_statements` after a clean return). A clean lease returns to the
  pool as-is: no `DISCARD ALL`, no reopen. Verified under `ReopenOnly` (SQL
  Server's real capability): five browses and a navigator expand cause 0
  resets and 0 reopens, while each raw request causes exactly one reopen.
  Mutation check: re-dirtying browse fails the R-036 test. Reopen rate is
  instrumented via `PgDriver::pool_stats()` (releases / resets / reopens /
  clean returns); nothing displays it yet. Not done here, from R-036's Action
  rather than the acceptance: the per-profile warm spare (budget work, T-042)
  and the best-effort T-SQL reset script for SQL Server (T-072's spike).
  Granularity is per raw request, not per statement — a raw `select 1` also
  counts as dirty. That is the conservative reading of "raw passthrough".
