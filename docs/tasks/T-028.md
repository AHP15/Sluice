- **Notes**: New crate `sluice-config`. The "no subprocess and no prompt" clause
  is enforced mechanically, not documented: `tests/no_subprocess.rs` scans the
  inert modules for process-spawning and prompting symbols and fails the build
  on any hit, and a third test asserts every module in `src/` is classified
  either inert or (T-029's) consent-gated, so a new module cannot quietly land
  outside the split D-026's safety argument rests on. It has already earned its
  keep twice — it caught a `std::process::id()` in this task's own test helper
  (rewritten to use a timestamp rather than weakening the ban), and the
  credential lint from T-022 independently forced `ConnectionUrl.password` to be
  `Secret<String>`.
  Decisions D-026/D-012 left open, resolved here and worth knowing: **precedence**
  is process env > `.env` > config files, and all candidates are returned in that
  order rather than one being silently chosen, because T-026 needs the list.
  **No upward walk** — only the named directory is scanned, since walking to the
  filesystem root reintroduces the ambient-authority shape R-001 is about.
  **Scheme allowlist** rather than "any URL", so a `homepage` or `registry` key
  in a config is not offered to the user as a database. **No `.env`
  interpolation or command substitution** (`${VAR}`, `$(cmd)` stay literal) —
  supporting them would put an evaluated mini-language in the tier D-026
  declared inert. Executable configs are recorded in
  `Discovery::executable_configs` and never read, which is the seam T-029 plugs
  into; a test writes a `drizzle.config.ts` containing `process.exit(1)` and an
  attacker URL and asserts neither takes effect.
