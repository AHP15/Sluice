## T-011: Dialect-aware script splitting used only for display attribution

- **Status**: done
- **Size**: M
- **Implements**: D-029
- **Mitigates**: R-040
- **Depends on**: T-010
- **Acceptance**: The user's script is sent verbatim to the engine as one batch with no client rewriting, a dialect-aware lexer attributes outcomes to text spans covering dollar-quoted bodies, `GO` separators, and semicolons inside literals and comments, and attribution falls back to ordinal-only with no highlighting when the split count disagrees with the engine's result count.

- **Notes**: R-040's rule is honoured structurally: the script is sent to Postgres
  VERBATIM as one `simple_query` batch and this module only computes spans into
  that same string, so a splitter bug cannot manufacture a syntax error the user
  did not write. Deliberate deviation, flagged: R-040 suggests `sqlparser-rs`
  "or equivalent"; this is a purpose-built lexer instead, because attribution
  needs exact UTF-16 offsets (a line/column token API would have to reconstruct
  them, adding its own bug surface) and because `GO` is a client directive no
  SQL parser tokenizes as a terminator. The corpus R-040 names is covered
  case-by-case in 13 tests: dollar-quoted bodies (`$$` and `$tag$`), `GO`
  separators including `GO 3` and `GO` inside a literal, semicolons inside
  string literals, doubled-quote escapes, quoted identifiers, T-SQL bracket
  identifiers, line and nested block comments, `E''` backslash escapes, and
  `$1` bind parameters not mistaken for dollar quotes. Verified live that a
  plpgsql body containing semicolons survives the batch. The safety net is what
  makes a lexer bug cosmetic: on count disagreement or low confidence, ALL
  outcomes degrade to ordinal-only with no highlighting — tested, including that
  a disagreement drops highlighting for every outcome rather than just the
  extra one.
