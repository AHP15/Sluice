- **Notes**: HELD AT in_progress DELIBERATELY — the workflow is written and
  covers all four targets on every push with AppImage as the Linux output and no
  signing credentials anywhere (unsigned by construction, not by omission), but
  **it has never run**: this is not a git repository and has no remote, so there
  is no evidence CI builds on macOS x86_64, Windows x64 or Linux x64. Claiming
  `done` would assert exactly the thing D-019 says this task exists to
  test — that cross-compilation is not silently broken — on three platforms
  where nothing has been executed. Locally validated on macOS arm64: the same
  `bun run tauri build` command CI runs produced `Sluice.app` and a 3.6MB
  `Sluice_0.1.0_aarch64.dmg`, ad-hoc/linker-signed only, i.e. unsigned per
  D-019. One real problem was found and fixed in the process: macOS DMG bundling
  drives Finder over AppleScript for window layout and fails with "Not
  authorized to send Apple events to Finder (-1743)" in any session lacking
  Automation permission. `CI: true` makes tauri skip the cosmetic step, and the
  workflow now sets it explicitly rather than relying on the runner default.
  Linux job pins ubuntu-22.04 for libwebkit2gtk-4.1, the D-019 compatibility
  floor. To finish: `git init`, push to a remote, and confirm all four jobs go
  green — the Linux webkit deps and the Windows MSVC toolchain are the untested
  surfaces most likely to need a fix.
  2026-11-06: still held — no remote yet. Fixed a workflow bug found on review:
  the build job's `rust-cache` pointed at `src-tauri -> target`, but the Cargo
  workspace root is the repo root and the target dir is `./target`, so every
