- **Notes**: `compile_update` builds each statement once, as segments (SQL
  text and parameter slots) plus the bound values, into a single artifact. The
  executed SQL is those segments with `$n`. `PlannedStatement.inline` is the
  same segments with display-only literals. Nothing rebuilds a statement from
  the edit set, and slots are never substituted into a rendered string (an
  identifier like `"$1"` would be corrupted). `inline` is `None` when any value
  can't be inlined faithfully: a backslash (its meaning depends on
  `standard_conforming_strings`), a control character, or more than 200
  chars. The preview then shows the parameterized statement and a bound-value
  table. New `Driver::preview_edits`, from the same `compile_edits` as apply,
  returns an `EditPlan` with a digest. `apply_edits` now takes
  `expected_digest`, which the Tauri command requires, and refuses before
  `BEGIN` if the edits recompile to a different plan (verified live after an
  `ALTER COLUMN TYPE` between preview and apply). Property tests: 3,000
  generated edit sets with hostile identifiers and values check that the
  statement is the segments, the slots are the params in order, each inline
  literal reads back as the bound value (NULL, quoting), SET column order
  follows the edit, and each slot carries its column's cast. Live: 60
  generated edits run as the inline preview text and through the real apply
  leave identical row state. Webview: Apply now opens `EditPreview` (the
  core's plan, text nodes only), staging is frozen while it is open, and only
  "Run N statements" executes, with the digest. Hand-rolled PRNG rather than a
  new proptest dependency.
