## R-043: D-010's row cap is per query, so it no longer bounds one execution

- **Severity**: medium
- **Likelihood**: medium
- **Disposition**: mitigate
- **Date**: 2026-07-31
- **Description**: The 10,000-row cap was written when one execution produced one result. An execution now produces a sequence, and a seed or migration script with fifty `INSERT ... RETURNING` or `SELECT` statements yields fifty capped results whose retained rows are held simultaneously across result panes -- half a million rows inside the budget the cap was supposed to enforce. The limit reads as protective in the record while bounding a unit that no longer corresponds to what the user runs, which is the same defect R-007 identified in bounding cardinality instead of bytes.
- **Disposition rationale**: Medium severity at medium likelihood, and it is the same defect R-007 identified — a limit bounding a unit that no longer matches what the user runs — so it gets the same treatment and should be built alongside it.
- **Action**: Guard: make the cap a per-*execution* budget rather than per-statement, covering rows and cumulative bytes (per R-007) and consumed in order across the outcome sequence. Statements late in a script are truncated once the budget is spent, with truncation surfaced on the affected outcome and the execution-level budget state shown so the user can see which statement exhausted it. Export-to-file remains the offered next action per D-010 and D-024. Mitigating tasks: T-050.
- **Related decisions**: D-029, D-010
