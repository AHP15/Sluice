## R-032: Scrubbing the subprocess environment breaks the configs the subprocess exists to read

- **Severity**: high
- **Likelihood**: high
- **Disposition**: mitigate
- **Date**: 2026-07-31
- **Description**: The reason a project has a `drizzle.config.ts` rather than a plain URL is almost always that it computes the connection from the environment -- `process.env.PGHOST`, `process.env.NODE_ENV`, a branch on deployment stage. Running that file under a minimal scrubbed environment does not make it fail loudly; it makes it take a different branch, so the config returns its default or its production fallback and the app connects somewhere the user did not intend. A security measure aimed at the code-execution path silently changes which database the tool opens, which is the more dangerous of the two failures.
- **Disposition rationale**: High severity and high likelihood, and it is the sharpest kind of defect — the security measure silently changes which database opens. But the intent behind scrubbing is to keep the *app's* secrets out of untrusted code, and that intent survives a precise scrub policy; the failure comes from the word `minimal` being unspecified.
- **Action**: Guard: specify the scrub as a denylist over the app's own additions, not an empty environment — the subprocess inherits the user's shell environment and the project's `.env` exactly as the user's own `node`/`bun` would see it, and the app strips only variables it itself injected plus anything holding resolved credentials or keychain handles. The config then takes the same branch it takes in the user's terminal. Back it with two loud-failure rules: a subprocess that exits non-zero, times out, or emits no parseable URL surfaces an error rather than falling back silently to the native path's guess, and the resolved connection target (host, port, database) is displayed before connecting so a wrong branch is visible rather than inferred. Mitigating tasks: T-031.
- **Related decisions**: D-026, D-012
