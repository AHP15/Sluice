## R-012: No connection-reset primitive is reachable on SQL Server, so session state leaks between browse queries

- **Severity**: medium
- **Likelihood**: high
- **Disposition**: fix
- **Date**: 2026-07-31
- **Description**: Resetting pooled connections on release depends on a per-engine primitive: Postgres has `DISCARD ALL`, and SQL Server has `sp_reset_connection` — but that is a TDS-level operation the .NET driver uses internally and `tiberius` does not expose. With no reachable reset, SQL Server browse connections carry `SET` options, temp tables, and `USE` changes from one query to the next arbitrary query, which is exactly the leakage the split model was designed to eliminate. `DISCARD ALL` additionally cannot run inside a transaction and is unavailable through PgBouncer in transaction mode.
- **Disposition rationale**: Medium severity at high likelihood, and it shares a root cause with R-011 — the decision assumed a primitive two of three engines do not expose — so the same supersession is the honest resolution rather than a separate guard.
- **Action**: Superseded by D-028 — a driver declares `reset: native | reopen | none`; where no reset primitive is reachable (SQL Server via `tiberius`, Postgres behind transaction-mode PgBouncer) the pool closes and reopens the connection on release instead of pretending it was reset, and `DISCARD ALL` is never issued inside a transaction. D-015 -> superseded.
- **Related decisions**: D-015, D-016
