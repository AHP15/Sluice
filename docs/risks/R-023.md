## R-023: Substring redaction of credentials fails on URL-encoded or split password forms

- **Severity**: medium
- **Likelihood**: medium
- **Disposition**: mitigate
- **Date**: 2026-07-31
- **Description**: Redacting errors before they leave the core will most naturally be implemented as "replace the known password string". That misses the password when the driver echoes back a percent-encoded connection string, when the value is split across a message and a `detail` field, when a TLS or DNS error quotes the URI differently, and when the password appears inside a nested source error's `Display`. Redaction that works in testing and fails on the specific error shapes that occur in production is a control that reports success while leaking.
- **Disposition rationale**: Medium severity at medium likelihood, but a redaction control that passes in testing and leaks on the error shapes that actually occur reports success while failing — so the guard has to be structural rather than a better substring match.
- **Action**: Guard: never construct a display or log form containing the password at all — connection strings are held decomposed with the password as `Secret<String>` and rendered from components, so on the app's own paths there is nothing to redact. For text the *driver* produces, add a defence-in-depth pass that walks the full error chain (`source()` recursion, `detail`, `hint`, nested payloads) and matches the password in raw, percent-encoded, and partially-quoted forms, redacting on a match anywhere. Back it with a fixture corpus of real error shapes — bad password, TLS failure, DNS failure, driver panic — each asserted to contain no credential substring in any encoding. Mitigating tasks: T-024.
- **Related decisions**: D-017, D-020, D-007
