## R-016: Unsigned rebuilds churn the macOS keychain ACL, and signing later can orphan stored secrets

- **Severity**: medium
- **Likelihood**: high
- **Disposition**: mitigate
- **Date**: 2026-07-31
- **Description**: macOS scopes keychain item access by application identity. An unsigned or ad-hoc-signed binary presents a different identity after each rebuild, so development produces a keychain authorization prompt on essentially every run, and "Always Allow" accumulates stale ACL entries. When Developer ID signing is added at distribution time the identity changes again, so items stored under the old identity may become inaccessible — meaning saved credentials break at exactly the release that was supposed to make the app distributable.
- **Disposition rationale**: Medium severity at high likelihood — the development-time prompt churn starts on day one and the release-time break lands at exactly the wrong moment — and both halves are addressable without revisiting the keychain decision itself.
- **Action**: Guard: development builds use a single stable ad-hoc signing identity so the keychain sees one identity across rebuilds rather than one per build. A keychain read failure is never fatal — the app falls back to prompting for the credential and re-storing it under the current identity. Add credential re-entry to the signing changeover as an explicit documented step, verified on a clean test machine, so the first Developer ID build is known to either carry items forward or prompt cleanly instead of discovering it at release. Mitigating tasks: T-071.
- **Related decisions**: D-007, D-019
