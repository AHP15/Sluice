## R-014: tokio-postgres rejects unknown type OIDs, so exotic types cannot reach the UI as strings

- **Severity**: high
- **Likelihood**: high
- **Disposition**: mitigate
- **Date**: 2026-07-31
- **Description**: The wire-value design promises that unfamiliar types — PostGIS geometry, `tsvector`, custom composites, domains, enums from extensions — cross as tagged strings. But `tokio-postgres` decodes the binary protocol through `FromSql` implementations and returns `WrongType`/unsupported errors for OIDs it has no impl for; there is no automatic stringify. Delivering the promise requires an explicit raw-bytes fallback path (or per-column text-format negotiation) that the decision assumes rather than specifies, and without it any table containing an extension type fails to browse at all.
- **Disposition rationale**: High severity and high likelihood — any table containing an extension type fails to browse at all — but D-006's promise is right and only the implementation path was left unspecified, so this is a gap to fill rather than a decision to change.
- **Action**: Guard: an explicit unknown-OID fallback in the Postgres driver rather than reliance on `FromSql` coverage — request text format for columns whose OID has no known mapping (or accept raw bytes through a permissive passthrough type) and emit the value as a tagged string with the type name resolved from `pg_type`. Cover PostGIS geometry, `tsvector`, domains, extension enums, and arrays of composites in D-021's type-fidelity corpus so the fallback is exercised rather than assumed. Mitigating tasks: T-017.
- **Related decisions**: D-006, D-002
