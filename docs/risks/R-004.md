## R-004: The optimistic-concurrency predicate silently no-ops on NULL and errors on non-comparable types

- **Severity**: high
- **Likelihood**: high
- **Disposition**: fix
- **Date**: 2026-07-31
- **Description**: `WHERE pk = ? AND col = <original>` never matches when the original value was NULL, because `col = NULL` is unknown in SQL — so every edit to a row with a NULL in the changed set reports a spurious conflict. Worse, Postgres' `json` type has no equality operator at all (unlike `jsonb`), so the same predicate raises `operator does not exist: json = json`. Arrays, floats, and `xml` have similar or ill-defined equality semantics.
- **Disposition rationale**: High severity and high likelihood: nullable columns are ubiquitous, so the predicate as specified fires spurious conflicts on ordinary edits, and on Postgres `json` it errors outright. The defect sits in the decision's stated mechanism, so a guard on top would leave the record self-contradictory.
- **Action**: Superseded by D-027 — optimistic concurrency now uses a null-safe comparison chosen per engine (`IS NOT DISTINCT FROM` on Postgres, an INTERSECT/OR-expansion form on SQL Server) and declares per-column concurrency-comparability, excluding types with no usable equality and telling the user those edits are protected by unique key only. D-009 -> superseded.
- **Related decisions**: D-009, D-006
