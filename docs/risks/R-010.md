## R-010: Composite-key keyset pagination degenerates to an unindexed OR-chain on SQL Server

- **Severity**: medium
- **Likelihood**: medium
- **Disposition**: mitigate
- **Date**: 2026-07-31
- **Description**: Keyset pagination over a composite primary key needs row-value comparison — `(a, b) > (?, ?)` — which Postgres supports and SQL Server does not. The fallback is an expanded OR-chain of range predicates, which the optimizer frequently cannot match to the index, turning each page fetch into a scan. The result is that pagination performs well on the engine used to develop it and collapses on the engine chosen to ship second.
- **Disposition rationale**: Medium severity at medium likelihood, and D-010 already carries the mechanism — a declared pagination strategy with a LIMIT/OFFSET fallback — so this extends an existing declaration rather than requiring new design.
- **Action**: Guard: the driver declares keyset support per relation rather than per engine, factoring in key arity — row-value comparison where supported, and where it is not, either an index-matchable rewrite validated against the real execution plan or an explicit fallback to LIMIT/OFFSET, with the strategy surfaced as D-010 already requires. Verify the chosen SQL Server form against an actual plan on a composite-key table before SQL Server browse ships, rather than assuming the optimizer matches the OR-chain. Mitigating tasks: T-048.
- **Related decisions**: D-010, D-022
