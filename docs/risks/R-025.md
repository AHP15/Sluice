## R-025: The UI offers sort universally, but Mongo sorts on unindexed fields fail at the memory limit

- **Severity**: medium
- **Likelihood**: high
- **Disposition**: mitigate
- **Date**: 2026-07-31
- **Description**: A generic grid presents every column as sortable because sort is part of the universal browse request. MongoDB performs a server-side sort within a 32MB limit when no index supports the sort, so clicking a column header on a large collection returns `Sort exceeded memory limit` rather than data. The same click is free on Postgres, so the contract's uniformity actively misleads the user about what the engine can do.
- **Disposition rationale**: Medium severity at high likelihood — the same click is free on Postgres and an error on Mongo, so the contract's uniformity actively misleads about what the engine can do — but the answer is to declare the difference, which is the pattern the design already uses everywhere else.
- **Action**: Guard: sortability is declared per relation and per path rather than assumed universal — the Mongo driver reports which paths are index-backed from `listIndexes`, and the grid marks non-backed columns as sortable-with-warning rather than rendering them identically to free ones. Set `allowDiskUse` where the operation permits it, and map the 32MB sort-memory error to a specific D-017 hint offering the index-backed alternatives, instead of surfacing a raw engine error. Mitigating tasks: T-065.
- **Related decisions**: D-004, D-005, D-018
