## R-042: Credit-based backpressure across a multi-result script pauses the server mid-transaction

- **Severity**: medium
- **Likelihood**: medium
- **Disposition**: mitigate
- **Date**: 2026-07-31
- **Description**: A script producing several `rows` outcomes must drain each result before the connection can advance to the next statement, and R-006's credit protocol makes draining depend on the webview retiring rendered rows. A user who scrolls away, switches tabs, or simply stops looking halts consumption, which halts the script between statements while its connection sits inside whatever transaction the batch opened. That is the idle-in-transaction condition D-010 called out as quietly harming the user's database, now reachable through ordinary UI inattention rather than through a forgotten explicit transaction.
- **Disposition rationale**: Medium severity at medium likelihood. The interaction is real — R-006's credit protocol is what makes UI inattention reach the server — but the fix is to break the coupling, which is a guard on the streaming layer rather than a change to either decision.
- **Action**: Guard: decouple socket draining from UI consumption for multi-statement execution. The core drains each result at server speed into a bounded spill buffer (memory-capped, disk-backed beyond the cap in the cache dir per D-014) and the credit protocol feeds the webview from that buffer, so the connection advances between statements regardless of whether anyone is looking at the grid. Apply D-028's idle-transaction rollback timer to script execution, not only to explicit editor transactions, and enforce the per-profile statement timeout across the batch so a paused script cannot hold a transaction open indefinitely. Mitigating tasks: T-052.
- **Related decisions**: D-029, D-010
