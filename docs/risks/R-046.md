## R-046: Through mongos, one profile's pool fills on every router, multiplying the budget

- **Severity**: medium
- **Likelihood**: medium
- **Disposition**: mitigate
- **Date**: 2026-11-07
- **Date resolved**:
- **Description**: D-035 rests on "only one server's pool is ever used" because `readPreference` is pinned to the primary. That holds for a replica set but not for a sharded cluster: server selection treats every `mongos` within the latency window as eligible and `max_pool_size` is per server, so a seed list or SRV name listing three routers (the norm for Atlas sharded clusters) lets application connections reach budget × routers. The budget D-028 exists to enforce is silently exceeded by a factor the user never sees, and the overhead D-035 declares counts only monitors.
- **Disposition rationale**: Medium severity at medium likelihood; D-035's model is right for replica sets and only needs a sharded-topology guard, not a new decision.
- **Action**: Guard: when the driver observes a sharded topology, size `max_pool_size` as max(1, budget / routers) so application connections across all `mongos` stay within the budget, and declare the split (routers, per-router cap) in pool stats and the usage UI. A live test against a two-router sharded cluster asserts the total never exceeds the budget. Mitigating tasks: T-114.
- **Related decisions**: D-035, D-028, D-034
