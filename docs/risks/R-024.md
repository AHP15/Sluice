## R-024: tiberius feature gaps block SQL Server as the second engine

- **Severity**: high
- **Likelihood**: medium
- **Disposition**: mitigate
- **Date**: 2026-07-31
- **Description**: The pure-Rust driver choice rests on `tiberius` being adequate, but it is a comparatively low-activity crate that does not cover the full TDS surface — attention/cancel handling is limited (already accepted), and Azure AD authentication, bulk copy, and connection reset are absent or partial. Since SQL Server was chosen as engine two precisely because it is needed day-to-day, a missing feature there is discovered at the worst moment, and the Bun-sidecar escape hatch with its mature `mssql` stack was deliberately removed.
- **Disposition rationale**: High severity at medium likelihood, which would normally suggest a defer — but essentially all of the cost here comes from discovering the gap late, so deferring is itself the failure mode. The guard is to buy the information early, while the escape paths are still open.
- **Action**: Guard: a time-boxed `tiberius` spike run *before* SQL Server browse work begins, against the actual SQL Server instances the owner needs day to day, proving the specific surface this design depends on — the auth modes actually in use, query cancellation, the reset/reopen path per D-028, TDS type coverage against D-021's corpus, and TLS behaviour. The spike ends in a written verdict; if it fails, the escape path is reopened explicitly (reorder to Mongo second per D-022's design-optimal ordering, or revisit D-001's no-sidecar rule for this one engine) rather than absorbed as slippage. Mitigating tasks: T-072.
- **Related decisions**: D-001, D-002, D-022, D-015
