## R-031: Consent keyed to the config file's hash ignores everything that file imports

- **Severity**: high
- **Likelihood**: medium
- **Disposition**: mitigate
- **Date**: 2026-07-31
- **Description**: Consent is invalidated when `drizzle.config.ts` changes content, but a config file's executable surface is its transitive import graph -- `./src/db/schema`, `./lib/env`, and every package it pulls from `node_modules`. Those change constantly through `npm install`, `git pull`, and lockfile updates while the config file itself stays byte-identical, so consent granted months ago silently authorizes code that did not exist when it was granted. A compromised transitive dependency in a repository the developer already trusted executes on the next `cd project && dbc` with no prompt.
- **Disposition rationale**: High severity at medium likelihood, and the decision's structure — consent scoped to a directory and revoked when the trusted thing changes — is right; only the definition of `the trusted thing` is too narrow. Broadening the fingerprint is an implementation guard, not a change of posture.
- **Action**: Guard: the consent fingerprint covers more than the config file — the config's own hash, the hash of every lockfile present (`package-lock.json`, `bun.lockb`, `pnpm-lock.yaml`, `yarn.lock`), and the hashes of local files reachable by a shallow, non-executing scan of the config's relative import specifiers. Any change re-prompts. Add a consent TTL (re-prompt after a period of disuse, e.g. 90 days) so stale trust expires on its own, and re-prompt whenever the resolved interpreter path changes. Residual, accepted knowingly: a malicious edit deep in the import graph that changes no lockfile and no directly-imported local file still inherits consent — the fingerprint narrows the window substantially but does not close it, and closing it fully would require resolving the graph, which means running the code. Mitigating tasks: T-030.
- **Related decisions**: D-026, D-012
