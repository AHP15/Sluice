## R-037: LRU release of an idle pinned session silently discards the state that made it pinned

- **Severity**: high
- **Likelihood**: medium
- **Disposition**: mitigate
- **Date**: 2026-07-31
- **Description**: Detaching the least-recently-used idle editor tab and reconnecting on next use hands that tab a different server session -- without its temp tables, `SET search_path`, session GUCs, or prepared statements. The user returns to tab 2 after working in tabs 6 and 7 and either gets `relation "#temp" does not exist` on a query that worked minutes ago, or worse, an unqualified table name silently resolves against the default search path and returns rows from a different schema. This is the exact behaviour D-015 named as unacceptable and forbade for connection loss; the supersession reintroduced it under a different trigger.
- **Disposition rationale**: High severity at medium likelihood, and the harm is concentrated entirely in the word *silently* — D-028 already forbids silent reconnect for connection loss, so applying the same rule to LRU release is a guard that makes the decision internally consistent rather than a change to it.
- **Action**: Guard, two parts. (1) Eligibility: a tab is LRU-releasable only if the app can show it holds no session state — no `SET`/`USE`, no temp table DDL, no prepared statement, no open transaction. State-holding tabs are ineligible and the new tab is refused instead, which is the rule D-028 already applies to transactions. (2) Visibility: a released tab is never silently reconnected. It shows a persistent banner naming what was released, and its next execution requires an explicit reconnect action, so a query can never run against a session the user believes is the old one. Note this makes refusal more common, which is the pressure R-038's guard exists to relieve. Mitigating tasks: T-043.
- **Related decisions**: D-028
