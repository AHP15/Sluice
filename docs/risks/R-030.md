## R-030: The SQL editor writes credentials into query history and logs, around the trust boundary

- **Severity**: medium
- **Likelihood**: medium
- **Disposition**: mitigate
- **Date**: 2026-07-31
- **Description**: The trust boundary keeps stored credentials out of the webview, but the query editor accepts credentials as ordinary query text: `CREATE ROLE x WITH PASSWORD '...'`, `ALTER LOGIN`, `db.createUser({pwd: ...})`, or a connection string inside a `postgres_fdw` or `dblink` call. That text is typed in the webview, persisted to query history, and included in verbose diagnostics — none of which the `Secret<String>` wrapper or the boundary redactor can see, because the value never took the credential code path.
- **Disposition rationale**: Medium severity at medium likelihood, and the value never takes the credential code path — so neither the `Secret` wrapper nor the boundary redactor can see it. The guard has to live on the history and logging paths themselves.
- **Action**: Guard: classify statements on the way into query history and verbose diagnostics, and redact literals in credential-bearing forms — `CREATE`/`ALTER ROLE|LOGIN|USER ... PASSWORD`, `db.createUser`/`updateUser`, and connection strings inside `dblink`/`postgres_fdw`/linked-server calls — persisting the statement with the literal replaced by `[redacted]`. Classification is conservative: an unparseable statement containing a password-like keyword is stored redacted rather than verbatim. Surface it in the UI when it happens so the user knows that history entry is not replayable, and apply the same filter before any statement text reaches a log file or the copy-diagnostics action. Mitigating tasks: T-025.
- **Related decisions**: D-007, D-014, D-020
