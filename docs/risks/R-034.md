## R-034: Null-safe comparison against a string original needs a per-type cast, and without one ordinary edits fail

- **Severity**: high
- **Likelihood**: high
- **Disposition**: mitigate
- **Date**: 2026-07-31
- **Description**: D-006 ships timestamps, decimals, big integers, uuids, and exotic types to the UI as tagged strings, so the `original value` fed back into `col IS NOT DISTINCT FROM $1` arrives as text. Postgres must then infer `$1`'s type: without an explicit cast it resolves to `text` and raises `operator does not exist: timestamptz = text`, and with a wrong or lossy cast the reconstructed value differs from the stored one and every edit reports a spurious conflict. Both outcomes are the failure R-004 was superseded to eliminate, reintroduced one layer down at the boundary between the encoding decision and the concurrency decision, where neither decision owns it.
- **Disposition rationale**: High severity and high likelihood — it reintroduces R-004's exact failure one layer down — but D-027 specifies the *comparison*, not how the original value is bound, so the gap is an unspecified implementation detail rather than a defect in the decision.
- **Action**: Guard: bind the original value with an explicit cast to the column's own type, taken from the type OID D-006's descriptor already carries — `col IS NOT DISTINCT FROM $1::<type>` — never letting the server infer the parameter type from a bare string. Prefer binary-format binding wherever the driver has a mapping, so no text round-trip occurs at all. Where a type's text representation is not provably round-trip-stable, route it into D-027's comparability exclusion rather than binding it and hoping. Extend D-021's type-fidelity corpus to assert the concurrency predicate specifically: for every type in the corpus, an unmodified row must produce a match (no spurious conflict) and a modified row must produce a conflict. Mitigating tasks: T-059.
- **Related decisions**: D-027, D-006
