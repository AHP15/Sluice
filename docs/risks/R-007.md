## R-007: A row-count cap does not bound payload size

- **Severity**: medium
- **Likelihood**: high
- **Disposition**: mitigate
- **Date**: 2026-07-31
- **Description**: The 10,000-row cap on raw queries bounds cardinality, not bytes. A query returning 10,000 rows each containing a 1MB `text` or `jsonb` column is tens of gigabytes and well inside the cap. Any table with document blobs, logs, base64 attachments, or wide denormalized JSON hits this, so the protective limit does not protect against the realistic version of the problem it was written for.
- **Disposition rationale**: Medium severity but high likelihood — any table with jsonb, logs, or blob columns hits it — and the guard is a small extension of a cap that already exists rather than new design.
- **Action**: Guard: cap cumulative serialized bytes as well as row count, whichever binds first, with the byte budget configurable alongside the row limit and truncation surfaced stating which limit tripped. Pairs with R-008's per-value ceiling: the byte cap bounds the result set, the value ceiling bounds any single cell. Export-to-file remains the offered next action per D-010. Mitigating tasks: T-050.
- **Related decisions**: D-010, D-006
