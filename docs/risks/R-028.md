## R-028: Unrecognized Postgres flavours fall through to vanilla catalog queries and fail mid-navigation

- **Severity**: medium
- **Likelihood**: medium
- **Disposition**: mitigate
- **Date**: 2026-07-31
- **Description**: Flavour gating works only for flavours enumerated in advance. Aurora reports itself as ordinary Postgres while differing in places; PgBouncer in transaction mode cannot be reliably identified from `version()`; new forks appear continuously. An unrecognized flavour is treated as vanilla, so its catalog divergence surfaces as an opaque error when the user expands a schema or opens a table — after a successful connect that implied everything was fine.
- **Disposition rationale**: Medium severity at medium likelihood. D-016 is right that flavour detection matters; the gap is that enumeration cannot cover forks that do not exist yet, so an unrecognized flavour must degrade visibly instead of being assumed vanilla.
- **Action**: Guard: pair version-string matching with capability probing at connect — run a small set of cheap catalog probes (partitioning, index methods, materialized views, `pg_stat` surface) and record what actually succeeded in the connection's capability descriptor, so behaviour follows what the server demonstrably supports rather than what its banner claimed. An unrecognized flavour is recorded and displayed as `vanilla, unverified`; catalog queries degrade to the probed-successful subset and render partial introspection with a visible note, so divergence surfaces at connect rather than as an opaque error mid-navigation. Mitigating tasks: T-055.
- **Related decisions**: D-016
