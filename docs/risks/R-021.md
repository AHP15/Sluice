## R-021: Capability flags proliferate until the UI is as coupled as the engine checks they replaced

- **Severity**: medium
- **Likelihood**: medium
- **Disposition**: defer
- **Date**: 2026-07-31
- **Description**: Forbidding engine checks in the UI moves each difference into a declared capability, but the differences are numerous — reset-on-release, cancellation semantics, keyset support, transactional DDL, case-sensitivity, sort limits, nested values, read-only enforcement. As the flag set grows the UI accretes conditionals over combinations that no engine actually produces, becoming untestable in aggregate. The coupling is relocated rather than removed, and the relocated form is harder to grep for than `if engine == "mongo"`.
- **Disposition rationale**: Medium severity at medium likelihood, and an accretion risk rather than a concrete failure — there is nothing to guard yet, and the alternative it replaced (engine checks in the UI) is worse today. It becomes real only at a flag count the design has not reached.
- **Action**: Defer with trigger: revisit when whichever comes first of (a) the capability descriptor exceeds 12 declared flags, (b) any single UI component branches on three or more capability flags, or (c) the third engine's capability descriptor lands. The question to answer at that point is whether flags should be grouped into a small set of named behaviour profiles the UI switches on, rather than combined pointwise.
- **Related decisions**: D-003, D-004
