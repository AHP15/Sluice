## R-009: The universal contains and eq operators return different results per engine

- **Severity**: medium
- **Likelihood**: high
- **Disposition**: mitigate
- **Date**: 2026-07-31
- **Description**: `contains` compiles to `LIKE '%x%'`, so a filter value containing `%` or `_` is interpreted as a wildcard unless escaped, silently matching rows the user did not ask for. Separately, string comparison case-sensitivity is a collation property: Postgres `LIKE` is case-sensitive while SQL Server's default collation is case-insensitive, so the same "universal" filter over equivalent data returns different row sets on different engines. The core operator set is syntactically portable but not semantically uniform, which is the property the UI actually assumes.
- **Disposition rationale**: Medium severity at high likelihood, but it is two problems with different answers: the wildcard leak is a straightforward correctness bug to close, while collation-driven case sensitivity is a database property a client should surface rather than override.
- **Action**: Guard, two parts. (1) `contains`/`starts with`/`ends with` always escape `%`, `_`, and the escape character in the bound value and emit an explicit `ESCAPE` clause, so filter text matches literally; users wanting wildcards use a separate driver-declared pattern operator. (2) Case sensitivity becomes a declared per-connection capability read from the server collation and shown in the filter bar, with an explicit case-insensitive toggle on string operators compiled per engine (`ILIKE` / `LOWER()` / collation clause). Accepted deliberately: the tool reports the engine's semantics rather than normalising collation across engines, which would destroy index usage. Mitigating tasks: T-015.
- **Related decisions**: D-005, D-004
