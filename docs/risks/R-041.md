## R-041: The outcome sequence carries no transactional context, so a partial-success report may be false

- **Severity**: high
- **Likelihood**: high
- **Disposition**: mitigate
- **Date**: 2026-07-31
- **Description**: `two successful outcomes and one error` describes what each statement returned, not what survived. Sent as one simple-query batch, Postgres wraps the script in an implicit transaction and rolls back statements one and two when statement three fails; sent statement-by-statement, each commits independently and statements one and two persist. The rendered result is identical in both cases, so the editor tells the user two statements succeeded when the database may hold none of their effects -- a preview-versus-reality divergence of the same class the staged-edit preview exists to prevent, on the path where the user is least able to check.
- **Disposition rationale**: High severity and high likelihood, and it is a preview-versus-reality divergence on the path where the user can least verify — but D-029 defines the envelope and adding the missing context to it is exactly the kind of gap a guard fills.
- **Action**: Guard: carry transactional context on the execution result, above the outcome sequence — which mode the batch ran under (implicit single transaction, explicit user transaction, or autocommit per statement) and, on failure, what was rolled back. Choose the mode deliberately per execution rather than inheriting the driver default, expose it in the editor before running (matching D-028's persistent transaction indicator), and derive the summary line from it: `statement 3 failed; statements 1-2 rolled back` versus `statement 3 failed; statements 1-2 committed` must be distinguishable at a glance. An outcome sequence that cannot state which of those happened is not renderable and should fail loudly in development rather than render an ambiguous summary. Mitigating tasks: T-012.
- **Related decisions**: D-029, D-017
