## R-026: Mongo $set on array indices and dotted field names writes to the wrong location

- **Severity**: medium
- **Likelihood**: medium
- **Disposition**: mitigate
- **Date**: 2026-07-31
- **Description**: Patching by path assumes paths are stable and expressible. Array positions are not stable — `items.2.qty` addresses whatever now sits at index 2, so a concurrent insert or an unrelated reorder makes the edit land on a different element than the one displayed. Field names containing `.` or starting with `$` (legal in modern MongoDB) cannot be addressed by dotted path at all, so those documents are silently uneditable or, worse, edit a different nested field that the path happens to name.
- **Disposition rationale**: Medium severity at medium likelihood, but a write landing on a different element than the one displayed is silent data corruption — so the guard must make the unsafe paths unreachable rather than merely warn about them.
- **Action**: Guard: at inference time (D-018) classify each path as editable or not. Paths addressing an array position, and paths whose field names contain `.` or start with `$`, are marked read-only in the grid with the reason shown; those documents are edited through the document view, which patches by whole-subtree `$set` at the nearest safe ancestor or uses the positional operator with a filter on the element's original value. Array-element edits always include the original element value in the update filter, so a concurrent reorder produces a surfaced conflict rather than a misplaced write. Mitigating tasks: T-062.
- **Related decisions**: D-009, D-018, D-006
