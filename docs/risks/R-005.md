## R-005: Cell editors reintroduce the precision loss the wire encoding prevents on read

- **Severity**: high
- **Likelihood**: high
- **Disposition**: mitigate
- **Date**: 2026-07-31
- **Description**: The read path protects `numeric(38,10)` and `int8` by shipping them as tagged strings, but the edit path routes them through a UI control chosen by *type class* — and both collapse into the `number` class. A JS number input or any `parseFloat` in the editor silently rounds the value before it is ever sent back, so the value survives display and is corrupted on write. The protection and the corruption sit two layers apart, which is why this passes casual review.
- **Disposition rationale**: High severity and high likelihood — the corruption is silent and lands on exactly the types D-006 went to trouble to protect on read — but the read-path decision is sound. The gap is that the edit path was never specified to preserve the same representation.
- **Action**: Guard: the type descriptor carries an `exact` marker for arbitrary-precision and 64-bit-plus numeric types, and the cell editor for those is a text control operating on the tagged string end to end — no `<input type=number>`, no `parseFloat`, no round-trip through a JS number anywhere between grid cell and bound parameter. Validation runs on the string (regex plus range check), never by parsing. Extend D-021's type-fidelity corpus to assert edit round-trips as well as reads, so the write path is covered by the same guard as the read path. Mitigating tasks: T-019.
- **Related decisions**: D-006, D-005, D-009
