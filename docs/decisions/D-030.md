## D-030: SQL Server cancellation: close-and-declare baseline, KILL only when verified

- **Status**: accepted
- **Date**: 2026-11-06
- **Date superseded**:
- **Date deprecated**:
- **Date promoted**:
- **Context**: D-010 requires a real cancel handle per query, with dropping
  the connection as the declared fallback where an engine cannot cancel
  cleanly. T-072 measured that `tiberius` has no TDS Attention API at all:
  dropping the query future left the connection hung and the server-side
  query still running. The only server-side lever, `KILL <spid>` from a second
  connection, needs `ALTER ANY CONNECTION` (which day-to-day accounts usually
  lack), rolls back the whole session's transaction, and targets a reusable
  session id.
- **Decision**: The SQL Server driver's guaranteed cancel is
  **close-and-declare**: on cancel it closes that connection's socket (never
  returning it to the pool) and the result is reported as "stopped waiting —
  the server may still be running it", never as "cancelled". It declares
  `cancel: kill_session` only when a probe at connect time confirms the login
  holds `ALTER ANY CONNECTION` (`HAS_PERMS_BY_NAME(NULL, NULL, 'ALTER ANY
  CONNECTION')`), and otherwise `cancel: none`; the UI words Stop
  accordingly. When `kill_session` is declared, cancel issues `KILL <spid>`
  from a separate connection **only after** verifying the target is still our
  session — matching `session_id` *and* the `connection_id` GUID captured from
  `sys.dm_exec_connections` when the connection was opened — then closes the
  original connection. Real TDS Attention support (in `tiberius` upstream or a
  maintained patch) is the intended long-term replacement and is tracked, not
  built now.
- **Rationale**: Close-and-declare needs no permissions and is always
  available, which satisfies D-010's declared fallback honestly; the UI tells
  the truth instead of implying the server stopped. `KILL` is the only way to
  actually stop server work today, but it is a heavier hammer that most
  accounts cannot use, so it is opt-in by verified capability rather than
  assumed — and verifying the connection GUID, not just the reusable
  `session_id`, prevents killing another user's session. Writing Attention
  support ourselves now would mean owning driver protocol code before the
  engine has shipped.
