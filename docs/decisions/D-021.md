## D-021: Unit tests and manual verification, plus a type-fidelity corpus

- **Status**: accepted
- **Date**: 2026-07-30
- **Context**: Driver code cannot be meaningfully unit-tested without real
  engines, but full testcontainers plus a shared conformance suite is
  substantial ceremony for a personal tool, and the SQL Server image alone is
  roughly 1.5GB needing 2GB of RAM.
- **Decision**: Default strategy is unit tests over pure logic (filter
  compilation, type mapping, argument grammar) plus manual verification by
  using the app. Add one exception: a per-engine type-fidelity corpus -- a
  fixture containing every type the engine has with hostile edge values
  (`int8` at maximum, 38-digit numerics, negative timestamps, text with NUL
  bytes and emoji, empty arrays, deeply nested jsonb, `Decimal128` extremes) --
  asserted to round-trip through D-006's encoding unchanged. Gate it behind an
  env var such as `TEST_PG_URL` so it runs against an existing Docker instance,
  skips by default, and needs no testcontainers or CI orchestration. React
  component tests over the grid and filter bar with fake data are worthwhile;
  Tauri end-to-end via WebDriver is not.
- **Rationale**: Introspection, pagination, and cancellation bugs fail loudly
  and manual use will find them. D-006 is the decision that fails *silently*:
  a numeric losing precision or a timestamp dropping its offset produces a
  plausible-looking wrong value, and manual verification is precisely the
  method that cannot catch it, because noticing requires already knowing the
  right answer. That single test is roughly a day of work and guards the most
  silently-breakable decision in the design. Consequence noted: without a
  shared conformance suite, D-022's Mongo stub check carries more weight as the
  guard on D-004's contract.
