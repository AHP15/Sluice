## D-029: Three-part contract with a statement-outcome sequence result model

- **Status**: accepted
- **Date**: 2026-07-31
- **Context**: D-004's contract required that all driver results be
  columns-plus-rows, with the grid and document viewer as two renderers over one
  shape. That shape cannot express the ordinary output of the query editor
  shipping in v1 (R-020): `CREATE TABLE` produces no result set, `UPDATE`
  produces an affected-row count, a multi-statement script produces several
  result sets in sequence, and a Mongo command produces a single status
  document. Forcing these into a rows envelope either fabricates empty tables or
  needs an out-of-band channel the contract never defined. The generic navigator
  tree and the structured browse request -- the other two parts -- are unaffected
  and carry forward unchanged.
- **Decision**: Drivers implement three things. (1) A generic navigator tree of
  typed nodes whose *kind* is driver-declared (`schema`, `table`, `view`,
  `collection`, `index`) rather than a hardcoded database/schema/table hierarchy.
  (2) A structured browse request -- relation reference plus filters, sort, and
  page cursor -- that every driver compiles into its native query. (3) Raw query
  passthrough in the engine's own dialect, always available.
  **Every execution returns an ordered sequence of statement outcomes**, one per
  statement the engine ran, each carrying the source statement's text span and
  one of four variants: `rows` (column descriptors plus streamed rows, as
  before), `affected` (a row count plus statement kind), `status` (a single
  document or message -- Mongo command results, `CREATE TABLE` acknowledgements),
  or `error` (D-017's layered error, per-statement). Structured browse always
  yields exactly one `rows` outcome, so the grid path is unchanged; the editor
  renders the sequence as tabbed or stacked result panes. A script that fails at
  statement three returns two successful outcomes and one error rather than one
  global failure, matching D-017's per-statement partial-failure model. The grid
  and document viewer remain two renderers over the `rows` variant. The UI must
  degrade gracefully on outcome variants and capabilities it does not recognise.
- **Rationale**: The single rows shape was an over-generalisation from the browse
  path, which genuinely is uniform, to the raw-query path, which genuinely is
  not -- and the wire model is the most expensive thing in the design to change
  later, so it is worth correcting before two engines build on it. A sequence of
  tagged outcomes costs the browse path nothing (it is a one-element sequence)
  while making DDL, counts, multi-statement scripts, and Mongo commands
  first-class rather than special-cased through an escape hatch. Per-statement
  errors inside the sequence also make D-017's partial-failure model reachable
  from the contract instead of only describable in prose.
- **Supersedes**: D-004
