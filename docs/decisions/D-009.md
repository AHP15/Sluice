## D-009: Staged edits with statement preview and DB-enforced safety modes

- **Status**: superseded
- **Date**: 2026-07-30
- **Date superseded**: 2026-07-31
- **Context**: Matching Drizzle Studio means editing data, which requires
  identifying rows, handling concurrent modification, and guarding destructive
  statements in a tool that will be pointed at production.
- **Decision**: Edits accumulate as pending changes, are previewed as the exact
  statements that will run, and are applied in a single transaction. Editing
  requires a unique key -- tables and views without one are read-only and say
  why. Optimistic concurrency via `UPDATE ... WHERE pk = ? AND <changed
  columns> = <original values>`, treating zero affected rows as a conflict to
  surface. Mongo edits use `$set` on touched paths, never whole-document
  replace. Per-profile safety mode enforced by the *database* (read-only role,
  read-only login, read-only user), declared as a capability so the UI knows
  whether the guarantee is real. A "production" profile flag requires typed
  confirmation for DDL and unqualified DELETE/UPDATE. Undo is
  discard-pending-changes only; there is no post-commit undo.
- **Rationale**: Without a unique key there is no safe UPDATE -- matching on
  all columns corrupts tables containing duplicates. The staged preview is the
  highest-value safety feature in the product because it converts "I clicked a
  cell" into "I read what this will do", and gives multi-row atomicity for
  free. Parsing SQL in-app to block writes is defeatable and must not be
  presented as a control; only a read-only connection is. Post-commit undo
  needs inverse statements and an undo button that sometimes cannot undo is
  worse than none. This decides target posture, not shipping order.
