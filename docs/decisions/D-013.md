## D-013: TypeScript config read via the user's own runtime

- **Status**: superseded
- **Date**: 2026-07-30
- **Date superseded**: 2026-07-31
- **Context**: D-012's config discovery wants `drizzle.config.ts`, but
  evaluating TypeScript correctly requires a JS runtime -- the file can import,
  compute values, and read `process.env`. That threatens to smuggle a JS
  runtime back into the shipped artifact, contradicting D-001's rationale about
  binary size and cross-compilation.
- **Decision**: Native Rust support for `DATABASE_URL`, `.env`, and plain
  JSON/TOML config. TypeScript config support is best-effort via shelling out
  to the user's own `bun` or `node` if one is on PATH, degrading to
  "choose a connection in the UI" when absent. Never bundle a JS runtime. Do
  not statically parse TS with a Rust parser.
- **Rationale**: A developer with a `drizzle.config.ts` has Node or Bun
  installed by definition, so the fallback essentially always works where it is
  wanted. Static parsing is the tempting middle path and the worst one: it
  handles literal cases and then silently produces the wrong connection for any
  config that computes or imports its URL. This resolution keeps D-001 intact
  rather than revising it -- the shipped artifact stays pure Rust and the
  enhancement uses a tool the user already has.
- **Superseded by**: D-026
