## D-027: Staged edits with null-safe, type-aware optimistic concurrency

- **Status**: accepted
- **Date**: 2026-07-31
- **Context**: D-009 specified optimistic concurrency as `UPDATE ... WHERE pk =
  ? AND <changed columns> = <original values>`. Plain `=` is unusable as
  written (R-004): `col = NULL` is unknown in SQL, so every edit to a row whose
  changed set contains a NULL reports a spurious conflict, and Postgres' `json`
  type has no equality operator at all, so the same predicate raises `operator
  does not exist: json = json`. Arrays, floats, and `xml` have ill-defined or
  absent equality semantics too. Everything else in D-009 stands; only the
  comparison mechanism was wrong.
- **Decision**: Edits accumulate as pending changes, are previewed as the exact
  statements that will run, and are applied in a single transaction. Editing
  requires a unique key -- tables and views without one are read-only and say
  why. Optimistic concurrency compares each changed column against its original
  value using a **null-safe** comparison chosen per engine (`IS NOT DISTINCT
  FROM` on Postgres, an `EXISTS (SELECT a INTERSECT SELECT b)` or
  `(a = b OR (a IS NULL AND b IS NULL))` form on SQL Server), never bare `=`.
  Each type class declares whether it is **concurrency-comparable**: types with
  no usable equality (`json`, `xml`, floating point, and any type the driver
  does not vouch for) are excluded from the predicate, the driver declares this
  per column, and the UI states that such an edit is protected by unique key
  only. Zero affected rows is a conflict to surface; a conflict on a row with
  excluded columns names which columns were unprotected. Mongo edits use `$set`
  on touched paths, never whole-document replace. Per-profile safety mode
  enforced by the *database* (read-only role, read-only login, read-only user),
  declared as a capability so the UI knows whether the guarantee is real. A
  "production" profile flag requires typed confirmation for DDL and unqualified
  DELETE/UPDATE. Undo is discard-pending-changes only; there is no post-commit
  undo.
- **Rationale**: The original predicate failed on the most ordinary data in any
  database -- a nullable column -- so the safety feature would have fired false
  conflicts constantly and taught users to distrust it, which is worse than no
  conflict detection at all. Null-safe comparison restores the intended
  semantics exactly, at no cost on either launch relational engine. Making
  comparability a *declared* property rather than a silent best-effort is what
  keeps the honesty D-009 was built for: the tool says "protected by key only"
  instead of quietly degrading, so the user knows which edits carry lost-update
  risk. Requiring a unique key, staging, previewing, and DB-enforced read-only
  are unchanged and remain the core of the posture.
- **Supersedes**: D-009
