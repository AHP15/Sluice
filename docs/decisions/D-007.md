## D-007: Credentials in OS keychain; the webview never receives secrets

- **Status**: accepted
- **Date**: 2026-07-30
- **Context**: The app connects to databases whose credentials must persist,
  while the webview renders arbitrary database content -- rows, column names,
  documents -- any of which may contain hostile strings. Where secrets live and
  which process can see them is the primary trust boundary.
- **Decision**: Secrets live in the platform keychain via the `keyring` crate
  (macOS Keychain, Windows Credential Manager, libsecret); non-secret profile
  metadata lives in a config file; the core resolves a profile id to
  credentials at connect time and never sends a credential outward. The webview
  holds profile ids and metadata only. Support reading `DATABASE_URL`-style
  environment variables, `.pgpass`, and `~/.pg_service.conf` so secrets need
  not be stored at all. TLS certificate verification on by default, with an
  explicit per-profile opt-out that shows a visible warning. Values render as
  text nodes only, never `innerHTML`; Tauri v2 capabilities stay minimally
  scoped. Encrypted-file fallback where no secret-service daemon exists.
- **Rationale**: Keeping secrets exclusively in the core makes an XSS in the
  webview "someone read one table" instead of credential exfiltration for every
  database ever connected to. A single encrypted store with a master password
  would work headless but makes the project own key derivation and unlock UX,
  and an unlocked session holds every secret in process memory. Plaintext
  config is readable by anything running as the user.
