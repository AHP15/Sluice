## D-005: Filter language: core operators plus driver-declared extensions

- **Status**: accepted
- **Date**: 2026-07-30
- **Context**: The structured browse request (D-004) carries filters, so the
  predicate vocabulary is part of the driver contract. Engine-specific
  operators (`ILIKE`, `~`, `@>`, `$elemMatch`, `$exists`) must be reachable
  without polluting the universal set or forcing users into raw SQL.
- **Decision**: A small universal core (`eq`, `ne`, `lt/lte/gt/gte`, `in`,
  `is null`, `between`, string `contains`/`starts with`/`ends with`) that every
  driver compiles, plus per-driver declared extension operators carrying id,
  label, arity, and applicable type classes. The wire model carries an AND/OR
  tree from the start even if v1's UI only produces a flat AND list. Map engine
  types into a handful of type classes (string, number, temporal, boolean,
  binary, json, array, geo, unknown) so the UI picks editors and operators
  without knowing engine-specific types. Filter values are always bound as
  parameters, never interpolated; Mongo values must never be interpretable as
  operator documents.
- **Rationale**: The same capability pattern as D-003, applied consistently, so
  adding an engine extends the filter bar rather than changing the UI. The
  AND/OR tree is over-built deliberately because the wire model is expensive to
  change and the UI is cheap. The type-class layer is what stops "one grid for
  all engines" collapsing into engine special-cases. Parameter binding matters
  less for malice than for a value containing a quote silently producing a
  valid but semantically wrong query.
