## D-014: Split app-state store: config file, SQLite, cache dir

- **Status**: accepted
- **Date**: 2026-07-30
- **Context**: D-011 committed profiles and saved queries to a portable
  human-editable file. Query history, tab and window state, column layout
  preferences, and inference caches still need a home, and their requirements
  differ sharply from profiles'.
- **Decision**: Three stores by role, located with the `directories` crate.
  Portable TOML/JSON in the config dir for profiles and saved queries; SQLite
  in the data dir for searchable query history; disposable JSON in the cache
  dir for UI and window state, which must be safe to delete. Version both
  durable stores from day one (`version` field, SQLite `user_version`), with
  forward migrations and a refusal to load a file written by a newer app
  version. Config writes are atomic (temp file plus rename). Importing a URL
  containing a password strips the password into the keychain and persists the
  URL without it. Query history is capped, purgeable in one click,
  opt-out-able per profile, defaults off for production-flagged profiles, and
  never enters a log file or bug report.
- **Rationale**: History grows unbounded and wants indexed search, which is a
  database's job; profiles want diffability and hand-editing, which SQLite
  prevents. Version-refusal matters even for one user, because two machines
  syncing one config file via git is exactly what D-011 enabled and an older
  build silently rewriting a newer file is how profiles get lost. Password
  stripping is what keeps D-007's trust boundary and D-011's "safe to commit"
  property true the first time a real URL is pasted.
