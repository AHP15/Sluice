## D-015: Pooled browse connections, pinned editor sessions

- **Status**: superseded
- **Date**: 2026-07-30
- **Date superseded**: 2026-07-31
- **Context**: Session-scoped state (`SET search_path`, temp tables, prepared
  statements) and explicit transactions interact badly with connection pooling.
  Sharing a pool either leaks that state between tabs or discards it on
  release, and both behaviours surprise users.
- **Decision**: Split by usage. Browse and grid traffic uses a pool per
  connection profile with a `DISCARD ALL`-equivalent reset on release, declared
  as a driver capability since not every engine has one. Each SQL editor tab
  pins a dedicated connection for its lifetime, so it behaves like a `psql`
  session. Transactions are opt-in per editor tab, never implicitly committed:
  entering transaction mode shows a persistent indicator, auto-rolls-back on
  idle timeout, and rolls back -- never commits -- on tab or window close. Pool
  max around 5 per profile, min 0, idle connections closed after a few minutes.
  Validate on checkout and reconnect transparently for browse; pinned sessions
  must surface connection loss explicitly rather than silently reconnecting
  into a session that no longer has its temp tables.
- **Rationale**: The split is what lets each side behave as its users expect
  instead of picking which surprise to ship; leaked or vanishing session
  variables are a classic homegrown-client defect. Idle-transaction rollback
  exists for the same Postgres VACUUM hazard noted in D-010. A dev tool
  occupying twenty slots of `max_connections` on a shared database is a bad
  citizen, and streaming results (D-010) holds a connection for its duration,
  so concurrent streams count against the ceiling.
- **Superseded by**: D-028
