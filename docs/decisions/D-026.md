## D-026: TypeScript config evaluated only under explicit per-directory consent

- **Status**: accepted
- **Date**: 2026-07-31
- **Context**: D-013 resolved TypeScript config support by shelling out to the
  user's own `bun` or `node`. Combined with D-012's working-directory
  discovery, that makes `cd <any-repo> && dbc` evaluate that repository's
  `drizzle.config.ts` automatically, in a process holding keychain access to
  every database the user has ever configured (R-001). The interpreter itself
  is also attacker-controlled, because a project-local `node_modules/.bin` or a
  planted `bun` earlier on PATH wins resolution.
- **Decision**: Native Rust support for `DATABASE_URL`, `.env`, and plain
  JSON/TOML config remains automatic and unprompted -- those are parsed, never
  executed. Evaluating a TypeScript or JavaScript config is a *code execution*
  action and is gated accordingly: the app never evaluates one without explicit
  user consent for that specific directory, shown as a dialog naming the config
  file's absolute path and the absolute path of the interpreter that will run
  it. Consent is remembered per canonical directory path in the config store
  and is invalidated when the config file's content hash changes. The
  interpreter is resolved only from absolute system locations (a user-configured
  path, or a system install directory) -- never from `node_modules/.bin`, never
  from a relative PATH entry, and never from anything inside the scanned
  directory. The subprocess runs with a minimal scrubbed environment, a
  timeout, and no access to the keychain, and only a connection URL is read
  from its stdout. Declining, timing out, or having no interpreter degrades to
  "choose a connection in the UI". Never bundle a JS runtime, and never
  statically parse TS with a Rust parser.
- **Rationale**: D-013's fallback was correct about *how* to evaluate a TS
  config and wrong about *when*: it inherited automatic invocation from a
  discovery path designed for inert files, so the blast radius of "I opened a
  cloned repo" became arbitrary code execution against every stored credential.
  Consent-per-directory keeps the genuinely excellent `cd project && dbc`
  ergonomics for the repositories a developer actually works in -- a one-time
  prompt per project -- while removing the drive-by case entirely, and
  content-hash invalidation means a config that starts importing something new
  re-asks rather than inheriting old trust. Absolute interpreter resolution is
  the other half: consenting to run `bun` must not mean consenting to run
  whatever the repository placed on PATH under that name.
- **Supersedes**: D-013
