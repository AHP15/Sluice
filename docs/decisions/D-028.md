## D-028: Capability-declared session model under one per-profile connection budget

- **Status**: accepted
- **Date**: 2026-07-31
- **Context**: D-015 specified a pool per profile with a `DISCARD ALL`-equivalent
  reset on release, plus a dedicated pinned connection per SQL editor tab. Three
  defects surfaced. The official `mongodb` crate hands out no individual
  connections at all, so neither half is implementable for the third launch
  engine (R-011). `tiberius` exposes no reachable reset primitive, so "reset on
  release" silently does nothing on the second engine and session state leaks
  between unrelated browse queries (R-012). And the two halves contradict each
  other: a ~5-connection budget plus one pinned connection per editor tab is
  already over budget at six tabs (R-013), which is the exact behaviour the
  design cited as its reason to reject connection-per-tab.
- **Decision**: Both connection affinity and connection reset become declared
  driver capabilities with defined behaviour when absent, and one budget governs
  everything.
  (1) **Reset**: a driver declares `reset: native | reopen | none`. `native`
  runs the engine primitive (`DISCARD ALL`). Where no primitive is reachable,
  the driver declares `reopen` and the pool *closes and reopens* the connection
  on release rather than pretending it was reset -- correctness is bought with a
  reconnect, not assumed. `none` is permitted only for engines with no
  session-scoped state to leak, and the UI surfaces it. `DISCARD ALL` is never
  issued inside a transaction, and a connection reaching release mid-transaction
  is rolled back first, then reset or reopened.
  (2) **Session affinity**: a driver declares whether it can pin a connection.
  Engines that can (Postgres, SQL Server) keep D-015's `psql`-like editor tab:
  a dedicated session for the tab's lifetime, opt-in transactions never
  implicitly committed, persistent indicator, auto-rollback on idle timeout,
  rollback -- never commit -- on tab or window close, and explicit surfacing of
  connection loss rather than silent reconnect. Engines that cannot (Mongo)
  declare `affinity: none`; their editor tabs run over the shared client, and
  the UI states that session-scoped state and interactive transactions are
  unavailable there rather than offering controls that cannot work.
  (3) **Budget**: one per-profile ceiling (~5, configurable) covers pooled and
  pinned connections *together*, not separately. Pinned sessions are allocated
  from that ceiling; when a new editor tab would exceed it, the least-recently-used
  idle pinned session is released (after rollback) and its tab is marked
  detached, reconnecting on next use, unless it holds an open transaction -- in
  which case the new tab is refused with an explanation. Pinned sessions idle
  past a timeout are released regardless. Pool min 0, idle connections closed
  after a few minutes, validate on checkout, transparent reconnect for browse
  only.
- **Rationale**: D-015's split was the right *goal* -- browse traffic and editor
  sessions genuinely want opposite behaviours -- but it was written as though
  every engine could supply the primitives, and two of three cannot. Declaring
  affinity and reset makes the gap visible at the contract instead of discovering
  it per engine, and `reopen` is the honest resolution for a missing reset: the
  cost is one reconnect, the alternative is a control that reports success while
  leaking `SET` options and temp tables into the next unrelated query. Folding
  pinned sessions into a single budget removes the internal contradiction and
  preserves the actual intent, which was never "5 pooled connections" but "this
  tool must not be a bad citizen on a shared `max_connections`". Refusing rather
  than evicting a transaction-holding tab is deliberate: silently dropping an
  open transaction is the one failure this model exists to prevent.
- **Supersedes**: D-015
