## D-008: Model transport variants and credential providers up front

- **Status**: accepted
- **Date**: 2026-07-30
- **Context**: Local and Docker databases connect directly; staging and
  production sit behind SSH bastions, socket proxies, or cloud IAM. Building
  tunnelling in v1 would consume weeks on key formats, agents, and passphrases
  before core browsing is solid, but the profile schema is versioned (D-014)
  and expensive to migrate.
- **Decision**: Ship direct connections only in v1 and document bring-your-own
  `ssh -L`. But model two things in the profile schema now: a `transport`
  variant (`direct` | `ssh-tunnel` | `proxy`) and a credential *provider* enum
  (`static` | `keychain` | `env` | `iam-token`) rather than a password string.
  When built-in SSH arrives, `known_hosts` verification is mandatory;
  trust-on-first-use is acceptable only if the fingerprint is displayed and the
  answer persisted.
- **Rationale**: AWS RDS IAM tokens expire in fifteen minutes and Azure AD
  tokens likewise, so a credential is a provider that may need refreshing
  mid-session, not a string fetched once. Encoding that as `password:
  Secret<String>` would make IAM support a rewrite touching every driver;
  encoding it as a provider makes it an added variant. Both models cost almost
  nothing today. A tunnel that silently accepts unknown host keys is a
  man-in-the-middle vector on exactly the path the tunnel was protecting.
