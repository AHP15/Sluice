## D-004: Three-part contract for relational and document engines

- **Status**: superseded
- **Date**: 2026-07-30
- **Date superseded**: 2026-07-31
- **Context**: Postgres tables and Mongo collections must share one UI without
  either forcing Mongo into a relational shape or duplicating the grid,
  filtering, sorting, and editing work per paradigm. This is the decision that
  determines whether new paradigms are cheap or structural.
- **Decision**: Drivers implement three things. (1) A generic navigator tree of
  typed nodes whose *kind* is driver-declared (`schema`, `table`, `view`,
  `collection`, `index`) rather than a hardcoded database/schema/table
  hierarchy. (2) A structured browse request -- relation reference plus
  filters, sort, and page cursor -- that every driver compiles into its native
  query. (3) Raw query passthrough in the engine's own dialect, always
  available, returning the same result shape. All results are columns-plus-rows
  with structured values; the grid and the document viewer are two renderers
  over one shape. The UI must degrade gracefully on capabilities it does not
  recognise.
- **Rationale**: The structured browse request is what makes one grid, filter
  bar, and pagination control work identically across engines -- the source of
  Drizzle Studio's uniformity. Relational-first would lose aggregation
  pipelines and nested documents and need an escape hatch for every subsequent
  paradigm. Per-paradigm UIs would rebuild virtualization, filtering, and
  editing multiple times, which is precisely the work worth amortising.
- **Superseded by**: D-029
