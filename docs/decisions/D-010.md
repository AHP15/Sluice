## D-010: Keyset pagination, capped streaming, and real cancellation

- **Status**: accepted
- **Date**: 2026-07-30
- **Context**: The implicit premise that result sets fit in memory is false --
  `SELECT *` against a 50M-row table is a normal accident, not misuse. The
  design must survive it, and a GUI must not degrade the user's database while
  doing so.
- **Decision**: Structured browse uses keyset pagination on the primary key
  (or `_id`), with the PK appended as tiebreaker when sorting by another
  column; views, aggregations, and keyless relations fall back to
  LIMIT/OFFSET, with the driver declaring which it used. Rows stream to the UI
  in incremental batches over a Tauri channel. Raw queries are capped (10k rows
  default, configurable) with truncation surfaced clearly and a separate
  stream-to-file export path that never materialises in the webview. Every
  query gets a real cancel handle; where an engine cannot cancel cleanly the
  fallback is dropping the connection, and that limit is declared in the
  capability descriptor. Default per-profile statement timeout.
- **Rationale**: Keyset stays fast at page 10,000 where OFFSET degrades
  linearly. Arbitrary SQL cannot be paginated without rewriting the user's
  query, so cap-and-export is the honest resolution rather than pretending
  pagination generalises. Server-side cursors would give snapshot consistency
  but pin a connection inside a long-lived transaction, and an
  idle-in-transaction Postgres session blocks VACUUM from reclaiming dead
  tuples -- a tab left open over lunch would quietly harm the user's database.
  Cancellation that abandons a still-running server query is a lie.
